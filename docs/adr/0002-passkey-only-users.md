# パスキーのみのユーザーを認め、復旧は管理者リセットで認証情報を全初期化する

> 強制パスワード変更中の扱い(パスキーを登録できない・現在のパスワードなしで変更できる)は [ADR 0003](./0003-temporary-password-and-reset-link.md) で置き換えた。

## 決定

- ユーザーの認証情報は「パスワード(0〜1)」と「パスキー(0〜n)」。**常にどちらか1つ以上**を持つことをサーバーで強制し、最後の1つを消す操作は拒否する。
- 「パスワード認証の無効化」はフラグではなく**パスワードの削除**とする。再び使うときは新しいパスワードを設定する。
- アカウント登録(最初の1人のブートストラップを含む)はパスワードとパスキーのどちらでもできる。どちらで登録しても、世帯の作成・招待コードによる世帯への参加は同じ処理を通る。
- パスキーのログインはユーザー名を入力しない方式(discoverable credential)とする。
- 認証情報の追加・削除には、既存の認証情報(現パスワードかパスキー)による直近5分以内の本人確認を要する(ログイン直後は確認済みとみなす)。削除系の操作では、操作した端末以外のセッションを破棄する。
- パスワードの変更では、パスワードを持つユーザーには直近の本人確認があっても常に現在のパスワードを求める(試行制限込みで検証)。直近の本人確認で代えられるのは、パスワードのないユーザーが新しくパスワードを設定する場合だけで、強制パスワード変更中は従来どおり現在のパスワードなしで変更できる。
- アカウント削除と super_admin による他ユーザーの削除は、操作者のパスワードが送られてくればそれを検証し、無ければ直近の本人確認を求める。パスキーのみのユーザーも操作できるようにするため。
- パスワードを検証する入口(本人確認のパスワード経路を含む)は、既存の認証試行制限を共通で通す。パスキーの署名検証(ログイン・本人確認)は対象外とする。
- 端末を失くしたユーザーは、**インスタンス管理者のパスワードリセット**で復旧する。リセットは従来どおり一時パスワードを発行して強制パスワード変更状態にし、同じトランザクションで**全パスキーを削除**し、全セッションを破棄する。

## 理由

- フラグで止める方式では、再び有効にしたときに漏れたかもしれない旧パスワードが復活してしまう。削除なら「ある/ない」の2状態で済む。
- 招待制・家族規模の運用のため、メールによる復旧の仕組みは持たない。復旧窓口は既存の管理者リセットに一本化する。
- リセットが必要になるのは、端末の紛失や乗っ取りのときがほとんどである。その時点のパスキーは信用できない(盗まれた端末や攻撃者が追加したものかもしれない)ため、すべて消す。
- 強制パスワード変更中は、パスワード変更とログアウト以外の操作(パスキーの追加や本人確認を含む)を許さない。リセットでパスキーは消えているので、まず新しいパスワードを設定してもらえば足り、その後に通常どおりパスキーを登録し直せる。

## 帰結

- 管理者がリセットすると、対象のユーザーは一時パスワードでログインしてパスワードを変更したあと、パスキーを登録し直す必要がある。パスキーのみだったユーザーも、リセット後はパスワードを持つ状態から再出発する。
- RP ID は公開ドメインに紐づくため、ドメインを変えると全パスキーが使えなくなる(そのときは管理者リセットで復旧する)。
- パスキー登録のチャレンジはプロセス内メモリに置くため、サーバーの再起動で進行中の登録・ログインは失敗する(やり直せば済む)。
