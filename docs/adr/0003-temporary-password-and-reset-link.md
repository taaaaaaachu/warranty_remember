# 管理者リセットの仮パスワードはパスキー登録でも解除でき、パスワードを決めないリセットリンクも用意する

ADR 0002 のうち、強制パスワード変更中の扱い(現在のパスワードなしで変更でき、パスキーの追加はできない)をこの ADR で置き換える。

## 決定

- 管理者リセットでサーバーが生成するパスワードは、従来どおり常に**仮パスワード**になる(管理者に選択肢はない)。仮パスワードでログインしたユーザーは、次のどちらかを済ませるまでログアウト以外の操作ができない: (a) 仮パスワードと異なる新しいパスワードを設定する、(b) パスキーを登録する(仮パスワードは削除され、パスキーのみのユーザーになる)。
- 強制はサーバー側(`hooks.server.ts`)で一律に行う。ページは変更画面へ戻し、API はパスワード変更・パスキー登録と、その前の本人確認以外を 403 にする。保証登録の閲覧もできない。
- 仮パスワードからの変更では現在のパスワードを求めず、直近の本人確認で代える(ログイン直後なら済んでいる。時間が経っていれば仮パスワードで本人確認を挟む)。新しいパスワードは仮パスワードと同じものを拒否する。
- インスタンス管理者は代わりに**リセットリンク**を発行できる。認証情報の初期化(パスワード・全パスキー・全セッション)は**発行時ではなくリンクを使った時点**で行う。リンクを開いた本人は新しいパスワードかパスキーのどちらかを設定し、その端末でそのままログインする。リンクで設定したパスワードは仮パスワードにしない。
- リセットリンクは 24 時間固定・単回使用で、1 人につき最新の 1 本だけが有効。再発行や仮パスワードの発行をすると未使用の古いリンクは使えなくなる。トークンは DB にハッシュで保存し、URL は発行直後に一度だけ表示する。対象者が削除されたときだけリンクも消え、発行した管理者が削除されても有効のまま。
- 仮パスワード中のユーザーでもリセットリンクのページは開ける(同じブラウザで別のユーザーのリンクを開く場合のため)。
- 対象にできる範囲は従来の管理者リセットと同じく、インスタンス管理者による自分以外のユーザー。自分自身はどちらの対象にもできない。

## 理由

- 管理者が知っているパスワードを本人が使い続けられる状態は残したくない。
- ADR 0002 ではリセット直後のパスキー登録を禁じていたが、端末を失くしたパスキーのみのユーザーは、パスワードを経由せずにパスキーのみの状態へ戻れるほうが自然。登録したパスキーは仮パスワードでの本人確認を経ているので、本人がパスワードを設定するのと同じ扱いでよい。
- 仮パスワードはログインに使った直後なので、もう一度入力させても防げるものがない。ただしログインしたまま時間が経ったセッションでは、通常の認証情報の追加と同じく本人確認を挟む。
- 発行時に初期化すると、本人がリンクを使わなかった・送り間違えた場合に、本人のログインを無駄に壊してしまう。乗っ取りの疑いがあって即座に締め出したいときは、仮パスワードの発行を使えばよい。
- メールは使わない(ADR 0002)。リンクは管理者がメッセージアプリなどで本人に渡す。

## 帰結

- 仮パスワードのユーザーは、変更を済ませるまで保証登録の閲覧もできない。
- リセットリンクの URL を見失ったら再発行する(DB からは復元できない)。
- マイグレーションで `reset_links` テーブルが増える。既存の強制パスワード変更中のユーザー(`must_change_password`)は、そのまま仮パスワードのユーザーとして扱われる。
